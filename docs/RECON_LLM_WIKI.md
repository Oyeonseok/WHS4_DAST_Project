# Recon LLM Wiki 사용 안내

Recon LLM Wiki는 기존 Recon DB와 참조 DB를 로컬에서 정리하고, 같은 기준으로 엔드포인트 커버리지를 비교하는 기능입니다. 공개 자료에서 가져온 정보가 실제 실행에서 발견된 정보로 섞이지 않도록 출처를 남깁니다. 기존 Scope → Recon → 후속 단계의 실행 순서를 바꾸지 않습니다.

## LLM Wiki를 어떻게 적용했는가

[Karpathy의 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)는 원본 자료와 이를 바탕으로 관리하는 위키를 분리하는 지식 관리 패턴입니다. 이 프로젝트는 그 패턴을 Recon 결과의 출처 관리와 오프라인 비교에 적용합니다.

원본 DB에서 추출한 자료는 `raw/`에 보존하고, 사람이 읽을 수 있는 요약과 연결은 `wiki/`에 둡니다. 새 자료를 반영한 이력과 비교 결과도 파일로 남겨 이전 실행과 다시 대조할 수 있게 합니다.

현재 CLI의 초기화·수집·비교·검사는 결정론적인 로컬 처리입니다. 이 명령들이 LLM API를 호출하거나 모델을 학습시키지는 않습니다. 위키를 만들었다고 기존 Recon Agent가 자동으로 읽거나 요청 대상이 늘어나지도 않습니다. LLM으로 위키를 해석하거나 요약하는 작업은 아래의 별도 검토 절차로 사용할 수 있습니다.

## 무엇을 100%로 측정할 수 있는가

소스 기반 목록은 특정 버전의 코드나 명세에 기록된 엔드포인트입니다. 런타임 발견 목록은 특정 실행의 로그인 상태, 승인 범위와 요청 예산 아래에서 도구가 관찰한 엔드포인트입니다. 두 목록은 같은 종류의 증거가 아닙니다.

| 항목 | 의미 | 의미하지 않는 것 |
| --- | --- | --- |
| 소스 목록에 존재 | 코드·명세 등에 해당 메서드와 경로가 기록됨 | 배포되어 접근 가능하다는 증명 |
| 런타임 목록에 존재 | 실행 결과 DB에 해당 엔드포인트가 기록됨 | 모든 기능 실행이나 취약점 확정 |
| 기준 목록과 일치 | 같은 비교 키로 기준 목록과 관측 목록이 겹침 | 기준 목록 밖의 기능까지 모두 발견 |
| 비교 커버리지 100% | 고정한 기준 목록의 비교 대상이 모두 일치함 | 서비스 전체의 완전한 정찰 |

비교에는 HTTP 메서드를 포함해야 합니다. `GET /account`와 `POST /account`는 별개 항목이며, GET만 관찰했다고 POST를 발견한 것으로 계산하지 않습니다. 호스트, 포트, 경로와 앱 버전도 맞춰야 합니다. 정적 리소스 수가 많아지는 것만으로 앱 기능의 커버리지가 높아지지는 않습니다.

기본 비교에는 실제 응답으로 확인된 경로와 함께, 대상이 제공한 HTML·JavaScript·OpenAPI 문서에서 수동적으로 선언된 후보 경로를 포함합니다. 선언 후보는 발견 커버리지에는 포함되지만 실제 접근 성공이나 취약점의 증거는 아닙니다. 정적 리소스 등 서비스 경로가 아닌 제외 항목은 기본 비교에서 계속 제외됩니다.

OpenAPI를 관측한 경우에는 계약에 직접 적힌 경로와 별도로, 계약의 구조에서 근거를 찾을 수 있는 제한된 경로군 후보도 보존합니다. 현재 규칙은 `/api` 컨트롤러 별칭, 버전이 없는 인증 액션, 인증 UI 동반 경로, 리소스 랜딩·대시보드, 표준 IMDS 하위 경로입니다. 이 후보의 `source_tools`는 `passive_route_inference`이고, Recon DB의 관측 근거에는 `derivation_rule`과 `inferred_from`이 기록됩니다. Wiki의 raw snapshot에도 이 근거가 `candidate_evidence`로 복사됩니다. 이 항목은 실제 요청으로 확인되기 전까지 계속 `candidate`이며, 직접 선언된 OpenAPI 경로와 같은 증거로 표현하지 않습니다.

ffuf는 실행 시간과 요청률이 낮을 때 큰 사전의 앞부분만 검사하게 됩니다. 그래서 `.env`, 상태·대시보드·GraphQL·디버그처럼 여러 프로그램에서 공통으로 쓰이는 소수의 일반 경로를 먼저 검사한 뒤 운영자가 지정한 사전을 이어서 사용합니다. 이 우선 목록은 특정 프로그램의 소스 DB나 비교 보고서에서 만들지 않으며, 전체 ffuf 시간 제한은 모든 루트가 함께 소비합니다.

완전한 기준 목록을 확보하기 어렵고 인증 역할, 동적 경로, 기능 플래그와 배포 차이가 있으므로 실제 서비스 전체의 100% 발견은 보장할 수 없습니다. 먼저 동일한 버전과 범위에서 기준 목록 대비 누락을 재현 가능하게 측정하는 데 사용하세요.

## 1. 위키 초기화

저장소에서 현재 설치를 확인합니다.

```bash
aidast recon-wiki --help
aidast recon-wiki init --root result/ReconWiki/vulnbank
```

기본 파일 구조는 다음과 같습니다. 세부 파일명은 각 입력과 비교 결과에 따라 정해집니다.

```text
result/ReconWiki/vulnbank/
├── schema.md
├── raw/
│   └── *.json
└── wiki/
    ├── index.md
    ├── log.md
    ├── sources/
    │   └── *.md
    ├── targets/
    │   └── *.md
    └── comparisons/
        └── *.md
```

`schema.md`에는 출처 구분과 비교 규칙이 있습니다. `index.md`를 시작점으로 열어 자료를 찾고 `comparisons/`에서 비교 보고서를 엽니다. `log.md`에서 언제 어떤 자료를 반영했는지 확인합니다. Obsidian 같은 Markdown 뷰어는 선택 사항이며 일반 편집기로도 읽을 수 있습니다.

## 2. 승인된 자료와 기존 실행 결과 반영

이 명령은 로컬 DB를 읽습니다. 웹페이지를 자동 다운로드하거나 소스를 가져오는 명령은 아닙니다. 이미 확보한 DB에서 사용 권한과 버전이 확인된 자료만 선택하세요. 예시의 `/path/to/...`를 실제 DB 경로로 바꿉니다.

이번 실행 결과는 런타임 자료로 반영합니다.

```bash
aidast recon-wiki ingest /path/to/scan_example/Recon.db \
  --root result/ReconWiki/vulnbank \
  --kind runtime \
  --label scan_example
```

동일한 앱 버전의 소스에서 이미 만들어 둔 참조 DB는 소스 자료로 반영합니다.

```bash
aidast recon-wiki ingest /path/to/source-reference/Recon.db \
  --root result/ReconWiki/vulnbank \
  --kind source \
  --label vulnbank-source-reference
```

공개 취약점 정답이나 평가용 카탈로그가 섞인 DB는 별도로 표시합니다.

```bash
aidast recon-wiki ingest /path/to/benchmark-reference/Recon.db \
  --root result/ReconWiki/vulnbank \
  --kind benchmark \
  --label vulnbank-benchmark-reference
```

`--kind`는 사용자가 입력의 성격을 선언하는 값입니다. 잘못된 선언을 런타임 증거로 바꾸어 주는 검증 장치는 아닙니다. 소스에서 추출한 목록을 `runtime`으로 표시하거나 공개 정답 목록을 `source`로 감추지 마세요. 한 DB에 여러 종류의 자료가 섞였다면 해당 한계를 비교 설명에 기록해야 합니다.

로그인 쿠키, 토큰, 요청 본문이 담긴 원본 로그나 세션 폴더를 위키 자료로 전달하지 마세요. 이 기능의 입력은 엔드포인트 목록을 읽을 수 있는 DB이며, 별도의 Markdown·HAR·OpenAPI 직접 수집 기능은 아닙니다.

## 3. Recon 실행 결과를 연결하는 방법

새 스캔은 기존 [Recon 사용 흐름](../README.md#recon)과 [운영 문서](OPERATIONS.md)의 승인 절차로 실행합니다. 위키 초기화나 소스 반영은 실행 승인에 해당하지 않습니다.

이미 한 사이클이 완료됐다면 다시 스캔할 필요 없이 그 실행의 `Recon.db`를 반영하면 됩니다. 대시보드에 표시된 scan ID와 실행 결과 폴더의 scan ID가 일치하는지 먼저 확인하세요. 기본 결과는 `result/Runs/<platform>/<program>/<scan_id>/` 아래에 저장됩니다. 예전 실행은 평면 경로에 있을 수 있으므로 기존 DB를 옮기거나 덮어쓰지 마세요.

후속 `Pipeline.db`에는 추가 분석 정보가 있을 수 있습니다. Recon 발견량을 비교할 때는 가능한 한 해당 실행의 원본 `Recon.db`를 사용하고, 양쪽 입력의 성격을 같게 유지하세요.

새로 완료된 실행을 `--kind runtime`으로 반영하면 이전 실행을 지우지 않고 자료 이력을 추가할 수 있습니다. 위키 자체는 네트워크 요청, 인증 처리, 후보 재실행을 시작하지 않습니다.

### 웹 대시보드에서 누적·비교하기

대시보드에서 시작한 스캔이 완료·실패·취소 상태에 도달하면 해당 `Recon.db`는 프로그램별 Wiki에 런타임 자료로 자동 누적됩니다. 이 자동 단계는 기준 DB를 읽거나 비교하지 않으므로 실행 중 정찰 입력에는 영향을 주지 않습니다. 완료된 스캔을 선택하면 **Recon Wiki 누적·비교** 영역이 표시됩니다. 다음 순서로 사용합니다.

1. **논리 대상/버전**에 같은 배포임을 확인할 수 있는 값(예: `vulnbank@전체_COMMIT_SHA`)을 입력합니다.
2. 자동 누적 상태를 확인합니다. 필요하면 **현재 Recon.db 누적**을 눌러 같은 원본을 멱등하게 다시 반영할 수 있습니다.
3. 실행이 끝난 뒤 소스 또는 평가 기준 `Recon.db`를 선택하고 **누적 후 기준과 비교**를 누릅니다.
4. 화면에서 누적 엔드포인트 수, Wiki 검사 결과, 정확 일치율과 누락 수를 확인합니다. 상세 누락 목록은 표시된 비교 보고서에 보존됩니다.

기준 선택 목록에는 출처 종류가 `[source]` 또는 `[benchmark]`로 표시됩니다. 대시보드는 선택한 파일 경로를 브라우저에 노출하지 않고 결과 루트 아래 `Recon.db`에 부여한 식별자만 사용합니다. 실행 중인 스캔은 Wiki에 반영할 수 없으며 완료·실패·취소처럼 종료 상태가 확정된 뒤에만 반영할 수 있습니다.

화면의 **기준과 비교**는 새 정찰을 시작하지 않습니다. 이미 생성된 런타임 DB와 선택한 기준 DB를 오프라인으로 비교하므로 공개 기준 목록이 정찰 에이전트의 입력이나 공격 후보로 전달되지 않습니다. 같은 스캔을 다시 누적하면 출처 식별자를 기준으로 갱신하고, 다른 스캔은 기존 이력을 유지한 채 추가합니다.

## 4. 같은 기준으로 커버리지 비교

관측 DB에는 실제 실행 결과를, 기준 DB에는 같은 앱 버전의 소스 기반 참조를 지정합니다.

```bash
aidast recon-wiki compare \
  --observed-db /path/to/scan_example/Recon.db \
  --baseline-db /path/to/source-reference/Recon.db \
  --root result/ReconWiki/vulnbank
```

양쪽 DB의 target이 같아야 하며 기준 목록이 비어 있으면 비교를 거부합니다. 이 검사만으로 배포 버전까지 같은지 확인할 수는 없으므로 입력 버전은 사용자가 대조해야 합니다. 관측 DB를 `runtime`으로 반영하는 비교 명령이므로 실제 런타임 실행 DB만 `--observed-db`에 지정하세요.

같은 앱을 loopback과 공개 주소처럼 서로 다른 origin으로 기록했다면, 두 DB가 동일한 배포 버전을 나타낸다는 것을 확인한 뒤 논리 target ID를 명시할 수 있습니다. 이 값은 물리 origin을 덮어쓰지 않고 비교용 식별자로 별도 보존됩니다.

```bash
aidast recon-wiki compare \
  --observed-db /path/to/loopback/Recon.db \
  --baseline-db /path/to/source-reference/Recon.db \
  --target-id 'vulnbank@COMMIT_OR_VERSION' \
  --root result/ReconWiki/vulnbank
```

버전을 확인하지 않은 채 `--target-id`로 서로 다른 배포를 합치면 비율이 의미를 잃습니다. 가능한 경우 commit 전체 값이나 릴리스 버전을 사용하세요.

평가용 정답이 들어 있는 DB를 기준으로 사용한다면 출처를 유지하도록 `--baseline-kind benchmark`를 반드시 지정합니다. 기본값은 `source`입니다.

```bash
aidast recon-wiki compare \
  --observed-db /path/to/runtime/Recon.db \
  --baseline-db /path/to/benchmark-reference/Recon.db \
  --baseline-kind benchmark \
  --root result/ReconWiki/vulnbank
```

명령은 JSON 요약과 보고서 경로를 출력합니다. `baseline`은 비교 대상 기준 항목 수, `observed`는 관측 항목 수, `matched`는 양쪽에서 일치하는 항목 수, `missing`은 기준 목록에만 있는 항목 수입니다. `exact_recall`은 메서드와 경로가 모두 일치한 비율이며 `path_recall`은 메서드를 구분하지 않는 보조 지표입니다. 각 비율은 JSON에서는 0부터 1 사이 값으로 표시됩니다.

`wiki/comparisons/`의 보고서에서 메서드별 일치 수와 누락 목록을 확인합니다. 제외 사유와 개별 항목의 관측 상태는 `raw/` 자료에서 대조합니다. 필요할 때만 제외 항목을 함께 확인합니다.

```bash
aidast recon-wiki compare \
  --observed-db /path/to/runtime/Recon.db \
  --baseline-db /path/to/source-reference/Recon.db \
  --root result/ReconWiki/vulnbank \
  --include-excluded
```

제외 정책을 바꿔 얻은 비율은 기존 비율과 바로 비교하지 마세요. 제외 항목 포함 여부가 다른 비교는 별도 보고서로 저장되며, 보고서의 제외 조건을 함께 기록해야 합니다. 관측 목록과 기준 목록의 대상 호스트나 버전이 다르면 먼저 입력을 바로잡습니다. 경로가 비슷하다는 이유로 다른 메서드나 다른 origin을 같은 항목으로 수동 합치면 누락이 숨겨집니다.

이번 실행의 낮은 결과를 판단할 때는 엔드포인트 총합, 정적 리소스를 제외한 비교 대상, 기준 목록과 일치한 항목을 나눠 보세요. 공개 취약점 카탈로그의 개수는 엔드포인트 발견 개수의 분모로 사용하지 않습니다. 비교 보고서의 누락 목록은 오프라인 평가 결과이며 자동 탐색·검증 작업 목록으로 전달되지 않습니다.

## 5. LLM으로 질문하고 변경안을 검토

생성된 위키를 Codex 등의 에이전트에서 열어 설명을 요청할 수 있습니다. 다음처럼 분석 범위와 출처 규칙을 함께 적어 주세요.

```text
result/ReconWiki/vulnbank/wiki/index.md와 해당 비교 보고서를 읽어 주세요.
기준 자료와 런타임 자료의 차이, 메서드별 누락 비율, 버전·범위 불일치를 설명해 주세요.
모든 주장에 로컬 raw 자료 또는 비교 보고서의 경로를 붙여 주세요.
관측 사실, 소스에만 기록된 사실, 추론을 구분해 주세요.
원본 raw와 실행 DB는 수정하지 말고 요약 수정이 필요하면 먼저 변경안을 보여 주세요.
```

현재 CLI에는 LLM 변경안을 자동 제안·승인·반영하는 별도 명령이 없습니다. 에이전트가 Markdown 수정을 제안하면 diff를 확인하고, 다음 내용을 검토한 뒤 편집 도구로 반영하세요.

1. 런타임에서 관찰하지 않은 소스 항목을 “발견됨”으로 바꾸지 않았는지 확인합니다.
2. 각 주장에 해당 자료의 출처와 실행·버전이 남았는지 확인합니다.
3. 이전 자료와 충돌하는 내용이 삭제되지 않고 충돌 또는 오래된 자료로 표시됐는지 확인합니다.
4. 공개 정답을 근거로 독립적인 발견 성능이 개선됐다고 쓰지 않았는지 확인합니다.
5. 비교 수치가 원본 비교 보고서와 같은지 확인합니다. LLM이 새로 계산한 수치는 재검증합니다.

자동 생성 페이지는 후속 수집으로 다시 생성될 수 있습니다. 사람이나 LLM이 쓴 추가 해설은 별도 검토 메모로 관리하고, 원본 증거와 계산값은 그대로 보존하는 편이 좋습니다. 문서 요약은 증거의 가독성을 높이지만 실제 관측의 증거를 대신하지 않습니다.

## 6. 위키 검사

자료를 반영하거나 위키를 수정한 뒤 검사합니다.

```bash
aidast recon-wiki lint --root result/ReconWiki/vulnbank
```

검사 결과는 JSON의 `ok`와 `issues`로 표시됩니다. 문제가 없으면 종료 코드 0, 문제가 있으면 종료 코드 1을 반환합니다. 현재 검사는 스키마 파일, 출처 종류와 ID, 엔드포인트 목록 무결성, 원본 DB 변경 여부와 원본별 Markdown 페이지 존재를 확인합니다. 원본 DB가 다른 위치로 옮겨졌거나 없어졌다면 당시 DB의 재검증에는 한계가 있습니다.

검사에서 보고한 문제를 원본 자료와 대조하여 수정합니다. `raw/`의 내용이나 출처가 달라졌다면 변경된 파일을 정상 자료처럼 보이도록 고치지 말고, 검증한 입력에서 다시 반영하세요. 모든 Markdown 링크와 문장의 사실성은 별도로 검토해야 합니다. 검사가 통과했다는 사실은 LLM 문장 전체가 사실임을 증명하지 않습니다.

## 7. 공개 정답이 성능 평가에 섞이지 않게 하기

독립적인 런타임 발견 성능을 평가할 때는 실행 전에 그 모델에 공개 정답·소스의 전체 엔드포인트 목록을 주지 않습니다. 먼저 실행 조건과 결과를 고정하고, 실행이 끝난 뒤 오프라인 비교에서만 기준 자료를 사용합니다.

참조 목록을 사전에 알고 수행한 결과는 “참조 자료를 제공한 평가”로 따로 표시해야 합니다. 이전에 `import-recon`으로 소스나 벤치마크를 가져온 DB와 독립적인 런타임 DB를 같은 성능 수치로 비교하면 발견 능력이 과대평가될 수 있습니다. 이번 위키의 `source`, `runtime`, `benchmark` 구분은 이 차이를 기록하기 위한 것입니다.

평가 기록에는 적어도 앱 버전, 참조 자료 버전, scan ID, 입력 DB, 로그인 상태·역할, 승인 범위, 제외 정책과 요청 예산을 남깁니다. 같은 조건에서 새 런타임 실행을 비교해야 기능 커버리지의 변화와 입력 조건의 변화를 구별할 수 있습니다.

## 기능의 현재 범위

이 기능은 로컬 자료 보존, 출처가 연결된 위키 생성, 엔드포인트 커버리지 비교와 무결성 검사를 제공합니다. 함께 반영된 정찰 개선은 JavaScript의 명시적인 `POST`, `PUT`, `PATCH`, `DELETE` 호출을 수동적 경로 증거로 보존합니다. 이 과정은 해당 변경 요청을 실행하지 않습니다. 인증 탐색, 도구 요청 예산, Recon 계획 생성과 공격·검증 로직은 위키가 자동으로 바꾸지 않습니다. 따라서 위키를 적용했다는 이유만으로 거의 100%의 결과가 보장되지는 않습니다.

실제 개선 여부는 입력이 섞이지 않은 비교 보고서로 확인해야 합니다. 기준 목록의 품질과 동일한 평가 조건을 먼저 확보한 뒤, 반복 실행의 보고서에서 일치 수와 누락 사유가 어떻게 바뀌는지 읽는 것이 이 위키의 사용 목적입니다.
