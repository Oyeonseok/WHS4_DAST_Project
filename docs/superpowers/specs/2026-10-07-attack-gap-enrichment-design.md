# Attack 단계의 근거 부족 경로 보완 설계

## 목적과 성공 기준

기존 Recon에서 관측했으나 Attack 계획이 `insufficient_evidence`로 끝난 경로를 조용히 버리지 않는다. Attack Agent가 허용된 요청으로 부족한 입력 형태, 인증 맥락, 응답 동작을 확인하고, 새 관측으로 해당 경로의 공격 가설을 다시 만든다. 이미 계획된 경로도 한 가지 시험 변형이 음성이었다는 이유로 다른 메커니즘을 빠뜨리지 않는다. 이 변경은 취약점 판정 기준을 낮추지 않는다. 실제 finding은 독립적인 HTTP 근거와 재현 계약을 계속 요구한다.

비교 대상은 Juice Shop `scan_7dd42c44b6fa4aad9adb504587017fa5`와 VulnBank `scan_771f8c2a62e543b3bb6b28637ad974db`의 보존된 Pipeline.db다. 각각 `insufficient_evidence` 45건과 21건, finding 1건이다. VulnBank의 유일한 finding은 Validation `INCONCLUSIVE`이므로 finding 수와 `CONFIRMED` 수를 분리한다. 원본 DB와 기존 스캔의 Scope·정책 스냅샷을 수정하지 않고 복사본으로 평가한다.

성공은 (1) 근거 부족 경로마다 보완 작업 또는 구체적인 정책 차단 기록이 남고, (2) 보완 요청에서 새로 관측한 근거가 출처와 함께 저장되며, (3) 새 근거에 따라 공격 작업이 추가되고 실제 요청을 시도하고, (4) 기존 1건보다 finding 및 독립 검증된 finding이 늘었는지를 각각 보고하는 것이다. 수치가 늘지 않아도 원인을 작업별로 기록한다.

## 접근 방식

프롬프트만 완화하면 작업이 0개인 경로가 여전히 생긴다. Recon 전체를 다시 돌리면 이미 저장된 데이터를 이용해 Attack이 보완한다는 목적을 측정하기 어렵다. 따라서 기존 Attack 계획과 coverage 실행 사이에 **보완 단계**를 둔다.

1. 기존 계획 생성은 근거 있는 가설을 그대로 보존한다. 비제외 엔드포인트 중 `insufficient_evidence`이고 관측 참조가 있는 경로에 별도의 보완 작업을 생성한다. `not_applicable`과 정책 제외 경로는 자동 보완하지 않는다.
2. Attack Agent는 작업에 묶인 경로·메서드, `attack_surface_form`, 계정 참조, 부족한 근거 이유를 받는다. 먼저 저장된 HTML·스크립트·OpenAPI·요청/응답을 다시 분석한다. 부족하면 기존 guarded HTTP helper로 소수의 요청을 보낸다. 요청은 Scope의 허용 대상·메서드·배제 규칙·예산·식별 헤더를 그대로 따른다. 인증 요청은 확인된 credential reference만 사용한다. 상태 변경 요청은 확인된 요청 형태와 소유 테스트 자원이 있을 때만 실행하며 기존 승인 경계를 따른다.
3. 보완 결과는 Pipeline DB에 별도의 값 없는 근거로 저장한다. 원래 Recon 관측을 덮어쓰지 않고, `request_id`, 경로, 관측된 필드명·위치, 응답 상태·형태, 인증 참조 여부, 출처를 연결한다. 비밀 값이나 응답 본문 전체는 계획 입력에 복사하지 않는다. 실제 HTTP 결과가 없으면 필드와 인증 상태를 `observed`로 승격하지 않는다.
4. 보완 작업이 끝나면 해당 경로만 한 차례 재계획한다. 새 근거가 가설을 지지하면 기존 coverage manifest로 공격 작업을 생성한다. 여전히 가설이 없으면 보완 시도 횟수와 남은 장애 이유를 남기고 종료한다. 보완과 재계획은 경로당 한 번만 수행해 루프를 막는다.
5. 계획된 경로에서는 같은 입력에 대한 서로 다른 시험 목적을 별도 coverage 작업으로 남긴다. 예를 들어 로그인 필드의 단순 무효값 검사와 인증 쿼리 처리 변형은 각각 다른 목적이다. 한 작업의 음성 결과가 다른 목적을 `tested_negative`로 닫지 않는다. 과거 finding과 벤치마크 정답은 Agent의 계획 입력에 넣지 않는다.
6. 공격 및 Validation의 기존 게이트는 유지한다. 보완 작업은 finding을 만들거나 `tested_negative`로 표시하지 않는다. 공격 작업은 독립적인 HTTP 시도와 결과를 기록하고, finding은 재현 계약이 있을 때만 승격한다.

## 책임 경계

- `attack/recon_hypotheses.py`: 보완 후 재계획할 단일 경로의 컨텍스트를 만들고, 기존 가설을 중복 없이 보존한다. 같은 입력의 별도 시험 목적도 보존한다.
- `attack/surface_form.py`: 원래 Recon 근거와 출처가 확인된 Attack 보완 근거를 함께 투영한다.
- `orchestration/attack.py`: 보완 작업의 생성, 실행, 한 번의 재계획, 신규 coverage 실행 순서를 조정한다.
- Attack DB helper 및 별도 보완 Skill: 작업·HTTP 요청에 연결된 값 없는 근거만 커밋한다. Agent는 준비 작업과 취약점 Hunt 작업을 혼동하지 않는다.
- Pipeline schema: 작업 상태와 보완 근거를 복사본 DB에 영속화한다. 재개 시 완료된 요청을 중복 전송하지 않는다.

## 실패와 재개

정책 차단, 인증 참조 부재, 요청 형태 부재, 429, 예산 소진, 응답 불명은 서로 다른 결과로 기록한다. 응답 불명인 상태 변경 요청은 자동 재시도하지 않는다. 429나 차단은 취약점 부재의 근거가 아니다. 일부 보완 작업 실패는 다른 경로를 중단시키지 않지만, 정책·DB 무결성 오류는 해당 배치를 실패시킨다. 재개 시 같은 원본 관측·정책·보완 결과에는 같은 작업을 다시 만들지 않는다.

## 검증

- 단위 테스트: `insufficient_evidence` 경로에서 작업 생성, 제외 경로 미생성, 실제 request ID 없는 근거 거부, 비밀 값 차단, 단일 경로 재계획, 중복 요청 방지, 429/정책 차단 분류.
- 통합 테스트: 가짜 guarded helper 결과를 사용해 `보완 → 새 입력 근거 → 새 가설 → coverage 작업`을 검증한다.
- 기존 데이터 평가: 두 Pipeline.db를 복사하고 먼저 네트워크 없는 재투영 결과를 저장한다. 로컬 3001·5001 대상의 보완 요청과 공격을 정책 안에서 실행한 뒤, 경로별 신규 근거·계획·시도·finding·Validation 상태를 이전 기록과 대조한다. 동일 취약점의 중복 finding은 증가로 세지 않는다.

## 범위

Recon 기본 허용 메서드는 바꾸지 않는다. 이전 스캔의 승인 Scope, Handoff, Recon.db, Pipeline.db를 수정하지 않는다. 취약점 정답 키나 이전 finding을 Agent의 계획 프롬프트에 넣지 않는다. 기존 작업 트리의 무관한 수정은 보존한다.
