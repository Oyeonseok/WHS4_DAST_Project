# Validation 유형별 증거 규칙 설계안

2026-09-25 기준 [Validation 프로필 계약](../../src/aidast/skills/validation/library) 58개를 빠짐없이 분류했다. [규칙 등록부](../../src/aidast/validation/core/profile_evidence.py)에 58개 목표 효과와 B/S/A 필요 사실을 적용했다. [재생 사실 추출기](../../src/aidast/validation/core/evidence_facts.py)는 실행 계약과 어댑터 요약을 대조해 assertion 또는 OOB nonce의 구조적 사실을 만든다. Coordinator는 각 Blind assessment에 대한 `blind_profile_evidence_audit`을 DB에 봉인하고 최종 결정의 증거 목록에 포함한다. 감사 기록은 조건부 범위 적격성 Agent의 입력에서 제외한다. 현재 적용 모드는 **감사**이며 점수·판정 강제는 기존 `hunt-source-leak` 규칙에 한정된다. 기존 프로필 계약과 정답지의 해시·판정은 바뀌지 않는다.

## 공통 판정 계약

모든 규칙은 현재 단계의 무결성 검사를 통과한 BlindCase, 완료된 target·positive control·negative control, 실행 계약과 연결된 요청 장부만 사용한다. Agent의 설명이나 `signal_observed=true` 선언만으로 보호 효과를 인정하지 않는다. 각 양수 영향 축은 그 축을 뒷받침하는 **현재 단계 증거 ID**와 아래 사실 영수증을 인용해야 한다. 원점수와 적용 점수, 사용한 규칙을 모두 보존한다.

| 축 | 양수 점수의 공통 필요 조건 | 부족할 때 |
| --- | --- | --- |
| 경계 B | target의 효과와 negative control의 무효 결과에 더해, 누구의 어떤 경계가 넘어갔는지 식별한 영수증 | B를 0으로 제한 |
| 민감도 S | 단순 상태 코드·오류·필드 이름을 넘는 보호 데이터, 실행, 영속 상태 또는 명시된 보안 효과의 영수증 | S를 0으로 제한 |
| 요구 조건 A | 실제 성공 시 사용한 최소 역할·자격 증명·상호작용·요청 횟수·환경 조건의 영수증 | A를 0으로 제한 |

재현 여부 자체를 증명할 수 없으면 `INCONCLUSIVE` 또는 객관적인 blocker 경로로 보낸다. 축 근거만 부족하고 재현이 확인되면 해당 축을 제한해 `UNDERPOWERED` 가능성을 평가한다. 부족한 증거를 `DISPROVEN`으로 취급하지 않는다. Impact Development가 만든 새 증거는 개발 전 Blind 축의 소급 근거가 될 수 없다.

점수 0–3의 다음 의미는 **제안 기준**이다. 현 정답지와 실측 사례로 보정한 뒤에만 강제해야 한다.

| 점수 | 경계 B | 민감도 S | 요구 조건 A |
| --- | --- | --- | --- |
| 0 | 넘은 경계가 입증되지 않음 | 보호 효과가 입증되지 않음 | 최소 행위자 조건이 입증되지 않음 또는 높은 특권·복잡한 준비 필요 |
| 1 | 한 서비스의 보호 라우트·워크플로 경계 | 제한된 비밀 아닌 메타데이터 또는 낮은 영향의 보호 효과 | 인증된 역할·여러 준비 단계 필요 |
| 2 | 다른 사용자·테넌트·출처 또는 보호 리소스 경계 | 보호 객체·상태 변경·제한된 내부 데이터 | 낮은 권한 또는 공개 진입점에 알려진 경로·대상·상호작용 필요 |
| 3 | 관리자·시스템·서비스·내부 네트워크 경계 | 비밀 값, 임의 파일·명령 실행, 광범위하거나 중대한 영속 효과 | 별도 자격 증명·피해자 상호작용 없이 재현 가능한 단일 진입점 |

A=0의 두 이유(증거 부족과 높은 요구 조건)는 감사 코드로 구분한다. 점수 2·3은 단순히 assertion이 참이라는 이유로 부여하지 않는다. 범위와 효과 크기까지 영수증이 식별해야 한다.

## 사실 영수증과 실행 가능성

공통 영수증은 `case_id`, `stage_run_id`, `profile_id`, 계약 해시, target·control attempt/evidence ID, 검증한 assertion ID, 요청 장부 ID, 비밀 아닌 사실과 사실의 출처를 봉인한다. 현재 감사 기록은 재현 관측과 해당 증거·장부 ID를 저장하며, assertion ID는 `reported_assertion_ids`로 별도 표기한다. `facts`의 `assertion_differential`은 전체 검사 조건(경로·헤더·선택자·프레임 포함), 계약의 기대값 해시, target 3/5회·negative control의 결과가 일치했음을 뜻한다. `nonce_callback_differential`은 OOB attempt ID에서 재계산한 nonce와 콜백 요약이 일치했음을 뜻한다. 두 사실 모두 해당 채널의 요청·작업 장부 ID를 요구한다. 8 KiB DB 제한을 넘으면 보조 ID 목록을 먼저, 이후 선택적 사실을 잘라내고 누락 수를 기록한다. 경계 영수증은 기대 주체·실제 주체·리소스 소유자 또는 출처를, 효과 영수증은 보호 데이터 분류·변경 전후 상태·실행 표식을, 요구 조건 영수증은 사용한 역할과 준비·상호작용을 담아야 한다. 이 의미상 사실 영수증은 아직 생성되지 않는다. 원문 비밀 값은 저장하지 않는다.

현재 HTTP·브라우저·multipart·gRPC·WebSocket·동시성·OOB 어댑터는 assertion 결과와 요청 또는 작업 ID를 남긴다. 추출기는 ID가 있는 요약은 ID와, ID가 축약된 요약은 계약 순서·해시와 대조한다. 그러나 **객체 소유자, 브라우저 피해자 문맥, 영속 변경 후 재조회, 캐시의 독립 요청자, 콜백의 실제 발신 주체, 토큰의 암호학적 무효성**은 모든 프로필에서 구조화된 영수증으로 제공되지 않는다. 아래 표의 `추가 사실`은 해당 검증기·어댑터 계약이 생기기 전에는 Agent 서술만으로 채우지 않는다.

구현 방식은 세 가지를 비교했다. 프로필마다 독립 `if` 분기를 만드는 방식은 처음에는 단순하지만 58개 중복과 누락 위험이 크다. Agent 프롬프트만 강화하는 방식은 관측 사실을 기계적으로 확인하지 못한다. **권장 방식은 런타임별 사실 추출기 + 프로필별 proof predicate 등록부**다. 11개 실행/신호 계열의 공통 관찰을 재사용하면서 위 표의 58개 고유 보호 효과를 각각 강제할 수 있다.

각 등록 항목은 `profile_id`, `runtime_kind`, `target_fact`, `boundary_fact`, `sensitivity_fact`, `actor_fact`, `rule_version`을 가진다. 적용 시 계약 해시와 규칙 버전을 감사 기록에 함께 남긴다. target 3/5회와 positive·negative control이 완전하지 않으면 감사 상태를 `replay_not_grounded`로 기록한다. 필요한 의미상 사실 추출기가 아직 없으면 완전한 재현의 양수 축을 `needs_verified_fact`로 표시한다. 현재 감사 모드에서는 이 상태가 판정을 바꾸지 않는다. `disqualifiers`와 사실 추출기의 강제 동작은 후속 구현 항목이다.

| --- | --- |

## 전체 프로필 매핑

각 행의 **증명 조건**은 `target_expected_signal`을 실행 가능한 사실로 풀어 쓴 것이다. **추가 사실**이 없으면 표의 공통 규칙만으로 양수 축을 부여할 수 없다. `수동`은 현재 계약만으로 기계 판정을 정의할 만큼 구체적인 효과가 없다는 뜻이다.

## 구현 순서와 검증 기준

1. **관찰 사실 추출:** 런타임 11계열에 공통 `EvidenceFact` 영수증을 정의한다. 기존 assertion 결과만으로 구성 가능한 사실과 새 probe·재조회가 필요한 사실을 구분한다.
2. **프로필 규칙 등록:** 위 58행 각각에 고유 proof predicate와 B/S/A 필요 사실을 선언한다. 런타임 계열 규칙은 재사용하되, `target_expected_signal.kind`가 유일하므로 같은 신호 계열이라는 이유로 보호 효과를 동일하게 인정하지 않는다.
3. **감사 모드:** 기존 Agent 원점수·현재 판정과 규칙 평가 결과를 병렬 기록하고 정답지의 양성·음성 사례에서 누락/오탐을 측정한다. 특히 `hunt-misc`, `hunt-exceptional-conditions`, `hunt-tls-network`, `hunt-llm-ai`, `hunt-subdomain`에는 필요한 영수증이 생기기 전 자동 확정을 금지할 후보로 표시한다.
4. **단계적 강제:** 각 규칙이 양성·음성 후보와 경계 사례에서 검증된 뒤 해당 프로필만 활성화한다. 확인되지 않은 축은 0으로 제한하되, 전송·재현 자체가 불명확하면 `INCONCLUSIVE`로 남긴다. 과거 DB는 당시 계약과 판정을 보존한다.

`validate_rule_coverage()`는 패키지 계약 58개와 코드 등록부의 정확한 일치, 채널, 고유 목표 사실을 검사한다. 점수 0–3의 세부 수치와 의미상 사실 영수증 스키마는 축 제한을 강제하기 전에 기존 정답지·실제 Agent 실행으로 보정해야 한다. 현재 감사 기록의 `needs_verified_fact`는 미검증 상태이며, 취약점 부정 판정이 아니다.

## 정답지 보정 현황

[읽기 전용 보정기](../../scripts/calibrate_validation_profile_evidence.py)는 공식 후보 정답지의 최종 상태 라벨과 합성 전이 정답지의 축 라벨을 구분한다. 합성 6개 trial의 baseline/final B/S/A가 현 `evaluate_impact()` 임계값과 일치하는지 확인하며, 현재 DB의 감사 기록이 stage·profile·assessment 해시와 내부 인용에 연결됐는지 검증한다. `STATUS_MATCH`는 저장된 최종 상태와 공식 라벨의 일치만 뜻하며 독립적인 결정 증명을 검사하지 않는다. `VALID_BINDING`은 감사 기록의 해시·형식·내부 인용 결합만 뜻하며 실제 취약성이나 축 사실을 확인하지 않는다. 합성 6건은 Agent의 실측 축과 비교한 결과가 아니라 점수 임계값의 자기 일관성 검사다. **공식 정답지에는 58개 프로필별 축 점수가 없다.** 합성 축 점수는 `hunt-source-leak` 실습용이므로 생산 점수 제한의 근거로 승격하지 않는다. 따라서 보정기는 모든 프로필을 `audit`로 남기며, 추가 독립 축 정답이 생기기 전에는 자동 강제를 활성화하지 않는다.

[현재 기록된 보정 결과](../test-results/09.25/validation/PROFILE_EVIDENCE_CALIBRATION.json)는 감사 기능 도입 전 lab DB에 대한 기준선이다. 공식 상태 라벨 10건, 재생 준비 7건, 저장 상태 일치 1건, 합성 축/임계값 일치 6건이며, 새 감사 기록의 유효한 연결은 0건이다. 이전 실행 DB에 감사 기록을 소급해 작성하지 않았다. 새 Validation 실행 후 같은 명령을 다시 사용하면 구조적 사실 추출과 정답지 간격을 확인할 수 있다.

2026-09-26 [새 로컬 GET 기준선](../test-results/09.26/validation/PROFILE_EVIDENCE_BASELINE.md)에서는 통제 평가기로 7건을 재생하고 감사 기록 7건을 생성했다. `hunt-source-leak`의 비어 있지 않은 JSON 값 검사는 값을 저장하지 않는 `json_value_differential` 영수증으로 남는다. 독립 채점은 음성 6건 `PASS`, 양성 1건 `UNRESOLVED`이며, 양성의 민감도 제한은 유지된다. 보정기는 `--candidate-db`·`--answer-db`가 주어지면 출처와 최종 결정 증거를 검사하는 기존 독립 채점 결과를 결합한다. `--axis-labels`에 제공된 B/S/A 라벨은 봉인된 Blind 평가와 대조한 실측 적용 축에 대해 참고 비교만 수행한다. 라벨의 출처는 검증하지 않으며, 합성 전이 정답지는 해당 인자로 받지 않는다. 현재 독립 축 라벨은 0건이다.

[실제 Agent 판정 실험](../test-results/09.26/validation/REAL_AGENT_ACCURACY.md)에서는 준비된 음성 6건이 재개 결과를 포함해 독립 채점 `PASS`였고, 양성 1건은 별도 Impact 실행 계약에서 `CONFIRMED` 및 전용 증거 채점 `PASS`를 받았다. 기본 실행은 양성 `UNDERPOWERED`, PrivacyRequests ClaimComparison 지연으로 끝나므로 이를 단일 설정의 7/7 정확도로 계산하지 않는다.

이후 [단일 실행 재검증](../test-results/09.26/validation/SINGLE_RUN_ACCURACY.md)은 Impact 계약이 있는 하나의 격리 DB에서 실제 Agent로 7건을 순차 실행해 일반 독립 채점 `PASS` 7/7과 Impact 전용 채점 `PASS`를 확인했다. Unblind는 봉인된 Blind 평가를 입력으로 하는 새 세션을 사용한다. 인증 전제 조건이 필요한 3건과 독립 축 정답 라벨은 여전히 범위 밖이다.
